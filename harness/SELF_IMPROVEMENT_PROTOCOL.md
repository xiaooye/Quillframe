# Runtime Self-Improvement Protocol · v6.6

Runtime behavior changes follow:

`Capture → Classify → Distill → Test → Promote → Version → Observe → Roll back`

## Evidence scopes

- one-run operational observation;
- runtime/project integration issue;
- user usage/cost preference;
- general runtime mechanism.

Project Canon and prose/style preferences remain owned by the project/policy source unless explicitly promoted through that source's own learning protocol.

## Promotion gate

A Generic Runtime change requires:
1. demonstrated mechanism/capability gap;
2. provenance/evidence;
3. smallest sufficient change;
4. capability/regression case;
5. conflict check against project/policy authority;
6. deterministic CI pass;
7. rollback point/version record.

Repeated model output or elapsed time is not new evidence.

## Negative evidence

User-rejected runtime behavior may become regression evidence. A failed model-generated workaround is never positive capability evidence merely because it existed.

## External frameworks

Framework/API updates produce adopt/adapt/reject candidates. Newer does not imply better. Do not copy another framework's authority or memory semantics wholesale.

## Event/connector learning

Webhook, connector, MCP or workflow telemetry may create observations/candidates only. Event frequency never grants promotion authority.

## Separation

Generic Runtime may learn execution mechanisms such as session persistence, idempotency, lease recovery, bounded handoffs and transport routing. It must not absorb a book's characters, Canon facts, plot plans or project-only prose rules.
