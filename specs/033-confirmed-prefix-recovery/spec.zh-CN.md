# 已确认前缀续跑规格

2026-08-31 · 已实现的 `SYSTEM-IMPROVE` 契约 · CH001 的真实续跑仍是单独的生产关卡。

本规格只处理一种窄场景：前一个 `REVISE` 已经生成同一份候选稿，前四道正文关卡全部通过，却因为自审返回的 JSON 语法不完整而停住。新的、由用户明确授权的修订 run 可以引用这段已确认前缀，从自审重新开始。它不会修补旧输出、改写旧 run，也不会扩大权限。

## 01 · 问题与决策

来源 run 已经为编辑计划、正文实现、读者体验检查和连续性检查付费，并确认它们都绑定同一份候选稿。第五次调用也返回了完整的模型响应记录，但响应不是合法 JSON。整章重跑会重复购买没有变化的证据；在旧 run 里继续，又会超过它已经冻结的调用上限。

因此采用新的 run：只引用已确认前缀，第一笔新调用就是全新的自审。Core 在创建 run 的同一事务中冻结前缀引用和用户授权。

## 02 · 严格适用边界

只有原生存储中的下列事实全部复验通过，来源 run 才可续跑：

- 它属于同一项目、同一目标，是已经静止的 `semantic_pending` 修订 run；
- 没有活动执行器、未决调用、候选稿、合格候选检查点、独立审稿交接、叙事提案或发布记录；
- 已确认调用顺序严格是：编辑计划、正文实现、读者体验、连续性、自审；
- 前四项全部通过，并绑定完全相同的候选正文与指纹；
- 第五项绑定正确的自审任务，但输出存在 JSON 语法错误；
- 只有一条对应的 `semantic_output_invalid` 事件，且明确记录未自动重试；
- 作者请求、执行请求、修订来源、上下文、修订计划、本地复用检查点、行文证据和阶段回执均为规范字节，指纹一致。

缺项、多项、乱序、额外调用、未决状态、取消状态、内容变化或证据冲突，都会在模型派发前拒绝。

## 03 · 权限与注册

调用方只能提供四项身份：来源 run、终止调用、预期候选指纹、预期前缀指纹。正文、判断、修订计划和“想复用哪些阶段”都不能由调用方塞入。

Core 要求：

- 任务模式必须是 `REVISE`；
- 修订来源必须与旧 run 中由 Core 冻结的来源一致；
- 必须有写入身份和幂等键；
- 授权意图必须精确为 `confirmed_prefix_recovery`。

Core 会重新推导私有前缀，冻结 `production_confirmed_prefix_source` 检查点，并单独记录授权回执。同一注册可幂等回放；同一幂等键下改变请求则冲突。

## 04 · 复用证据，不搬运调用

旧 `AgentJob` 与 `AgentResult` 永远归旧 run 所有，绝不插入新 run 的阶段日志。新 run 只写三份绑定当前上下文的复用回执，分别代表正文实现、读者体验和连续性；另写一份确定性复用检查点。每份回执都指向旧调用、旧结果和旧阶段回执的精确指纹，并声明当前 run 没有为该阶段调用模型。

复用前缀对新 run 的计费为零。新的主调用图固定为：

```text
新自审
→ 新修订对比
→ 新读者期待观察
→ 新叙事状态提案
```

本路线的 run 级主调用上限为四次。经理图到达 `awaiting_external` 后，再另行执行第五次、完全独立的审稿调用。

## 05 · 上下文、行文证据与语义隔离

不同 run 的身份字段天然不同，因此跨 run 比较使用规范化投影：来源集合、目标、作者偏好、档案和阶段选择必须一致。与此同时，新 run 的每份回执仍绑定当前上下文与冻结指纹。

旧行文快照只保留为历史生成证据。续跑不会再次消费一次性文风包，也不会重新打开 Writer 阶段。盲读者和独立审稿仍看不到私有修订指令与文风选择数据。

旧的错误字节不会在本地被修补、整理或冒充判断。新自审必须调用当前登记的正式契约。

## 06 · 后续修订仍可复验

恢复得到的候选稿若将来再次成为修订来源，必须能重建完整的逻辑日志：

- 正文实现、读者体验与连续性沿冻结的前缀引用和当前复用回执回溯；
- 自审、修订对比、读者期待和叙事状态仍是恢复 run 自己的真实调用；
- 合格判断、独立审稿、发布、谱系、候选字节和全部指纹继续一致。

逻辑日志指纹由恢复 run 的原生日志、已确认前缀指纹和三份复用回执指纹共同组成。这样既保留来源，也不会假装旧工作发生在新 run 中。

## 07 · 失败、回滚与非目标

证据变化、上下文变化、修订来源变化、授权不符、预算不足、新输出无效、独立审稿失败或取消，都会让续跑关闭。系统不会偷偷退回整章重写，也不会自动派发替代调用。

回滚时停止新的前缀续跑注册，保留所有新旧检查点、回执、事件、调用行与预算记录；既有 run 仍可审计。

本规格不负责：

- 自动语义重试或 JSON 修补；
- 提高旧 run 已冻结的调用上限；
- 复制或改派历史模型调用；
- 复用旧独立审稿；
- 接受、结算或提升正典；
- 把确定性测试当作文学认可。

## 08 · 对规格 032 的窄范围前向取代

规格 032 继续管理持久等待传输，也继续禁止自动重试。本规格只取代其中一个窄结论：遇到已确认的旧格式失败时，新 run 不必把整张生产图全部重跑。它仍然是新的、由用户明确授权的 run，但可以在 Core 完整复验后引用一段封闭前缀。旧 attempt 不会被伪装成活 worker，旧输出不会被修补，也不会增加未授权调用。

## 09 · 规范要求

- `CPR-001`：必须有用户明确授权与幂等键。
- `CPR-002`：调用方只能提交身份引用；私有证据全部由 Core 推导。
- `CPR-003`：来源必须满足严格的五调用封闭拓扑与语法失败边界。
- `CPR-004`：任何证据漂移都必须在派发前拒绝。
- `CPR-005`：绝不把旧阶段调用行复制进新 run。
- `CPR-006`：只计费四次新主调用与一次分开的独立审稿。
- `CPR-007`：不得再次消费历史一次性行文包。
- `CPR-008`：通过逻辑日志保证将来的作者修订仍可复验。
- `CPR-009`：继续禁止自动重试、接受、结算与正典提权。
- `CPR-010`：普通 CI 不运行真实模型。

## 10 · 完成真实性

工程完成要求确定性续跑、防篡改、预算、不复制、后续修订、持久等待和回归测试全部通过。真实完成还要求 CH001 只新增四次主调用，完成一次全新独立审稿，核对当前预算 Epoch，并由 Core 暴露一份尚未接受、尚未结算的 Review Draft。
