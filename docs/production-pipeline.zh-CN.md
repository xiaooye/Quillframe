# 生产流水线

Quillframe 的起草与修订（`DRAFT` / `REVISE`）不是固定次数的模型调用，而是一张自适应生产图。图上的边界是硬约束，但每一章不必机械地走完全相同的调用数量。

## 1. 冻结权威与稀疏上下文

解析本轮框架与项目的精确权威来源，建立会话和运行身份，只选择与当前任务直接相关的上下文，并验证阶段隔离和指纹边界。未来计划的结果不得提前进入当前状态；回退坏例和隐藏的预期标签不得污染第一遍正文生成。

目标章节及其所属全书的当前计划，在允许读取计划的规划与生产阶段属于绑定的任务输入。Core 将这些必需输入与模型按相关性选择的可选材料分开记录，选择器不能静默漏掉它们。权限、失效、故事时间和硬预算检查仍然适用；盲读与独立审稿包不会收到这些计划。绑定计划不意味着计划中的事件已经成为事实。

## 2. 正文之前先做场景模拟

故事与正典预检、人物私有行动推演、人物行动提案与场景行动结算，会先建立因果、人物意图、知识边界、压力和不断变化的选择。随后由已登记模型只投影 Scene Realization Contract、当前作者目标、短 Director Note 与最小合格 Writer 上下文的 ID；人物私有推演留在因果侧。Reader Pressure 在正文之前读取这份 Writer-safe 投影。

预检检查精确目标是否具备必需材料，以及拟创作内容是否违背既有事实或明确硬约束。原创故事可以从空正典开始。来源描述中的非权威标记不禁止当前工作单元提出内部提案，`db_fetch_performed=false` 也不否定已经提供的冻结内容；两者都不允许额外查询、不改变真实执行证据，也不授予写入权限。确实缺少必需材料或存在冲突时仍须失败；后续连续性检查针对候选正文，不把尚待作者采纳本身判为缺陷。被拒绝的运行保留原始判断，框架修复后必须另建运行。

### 原生输出结构约束

参考生产运行时会为 `character.action_propose` 和 `scene.resolve_actions` 请求原生 JSON 输出约束。约束只保留原契约各层已经必填的字段；有意义的动机、策略、阻力和代价仍可写进行动文本，不把可选字段改成必须填写的空值。问题、不确定性和阻断性修复建议都仍可表达。完整原契约及引用校验继续生效。

`AgentJob.output_schema` 将约束纳入真实请求指纹。OpenAI Chat Completions 与 Responses 协议明确传递该约束，Codex CLI 中继通过 [`--output-schema`](https://developers.openai.com/codex/noninteractive) 提交，保留结构文件及其哈希，并在发布响应前校验原始文本。多余尾部、重复 JSON 键、非有限数值或结构不符都会被拒绝，不修改返回内容、不自动重试。语义上“失败”的合法结果仍可正常传输，但不代表质量审查通过。

这只是有限的传输约束，并不支持任意 JSON Schema 或所有模型服务。开放键值对象、不支持的结构组合及当前 Anthropic 协议实现会明确报错。受约束的任务要求已有文字调用验证记录且协议已经解析的模型，不额外探测、不回退，也不因发出了结构化请求就把提供方能力标为已验证。未启用约束的任务不序列化新字段，旧指纹不变。已经派发的任务不能补上新约束再重放；应保留原证据，另建运行。测试夹具验证的是接线与拒绝行为，不是真实提供方验收或独立审稿。

## 3. 生成内部候选稿

单次 direct Surface Writer 根据紧凑 Writer Pack 直接实现正文；不存在先写一篇完整中间稿、再交给第二个模型重写的阶段。结果会立即冻结为带内容指纹的候选，并在精确 release gate 之前保持私有。

## 4. 独立评审之前先做资格检查

`quality/candidate_qualification.py` 要求已登记的非独立候选稿自检、读者投入度语义证据和连续性证据。只要候选稿经历过一次修订，还必须由 `quality.compare` 对目标约束集执行保持性比较。

输出只可能是 `awaiting_semantic`、`repair_required`、`qualified_for_independent`。资格检查本身不是独立评审，也不能替代独立评审。

## 5. 回到真正负责问题的机制修复

局部文字缺陷可以局部改写；成片的文字实现问题可以重新实现整段；“安全但平淡”的问题回到阅读牵引与场景模拟；人物失败回到人物模拟；故事或计划失败回到更上游；上下文失败则回到上下文与记忆机制。

每一轮修订都遵守**修复且保持**（`FIX + PRESERVE`）。局部目标改好了，但目标约束集、读者价值或人物关系能量被破坏，就不算整体修订成功。

### 修订未通过资格检查的内部稿件

只有 Core 验证了已停止的 `failed_gate` 运行、精确的内部候选稿及 `repair_required` 资格回执，Studio 才会提供**修订此版本**。该操作新建一个 `REVISE` 运行。Core 在同一事务中冻结原运行、检查点、候选稿字节、诊断和已确认的执行日志；浏览器只提交精确引用。原失败运行及其输出保持不变。

已绑定来源的运行可用 `inherit_repair_request=true` 调用 `author.run.execute`。原任务、读者牵引目标和规则材料由 Core 提供，注册时还会继承原运行选定的作者偏好。调用者不能替换这些目标，也不能预填“比较通过”。普通 `DRAFT` 仍须明确提交其执行输入。修改目标、来源上下文过期、候选证据缺失或传输故障，需要各自处理，不能借这个入口伪装成文字修订。

已登记的 `editor.repair_spec` 接收原稿和有限的诊断材料。目标约束集无损复制明确的原请求和冻结的有效计划，不从拒稿反推创作目标。模型决定修订层级、生成方式、要修复的问题和要保持的目标。全新生成的 Writer 只看到当前故事材料和这些约束，不收到原稿或完整批评轨迹；局部修订只会收到精确指纹绑定的编辑窗口。各项生产机制都会在新运行的日志和预算下重新执行。

生成后，已登记的 `quality.compare` 接收新旧两稿的真实文本及经过校验的 SHA-256 指纹，分别判断缺陷改善与目标保持，再交给现有资格门。修订保留最初的比较谱系，全新生成则没有文本父级。比较发现退步或证据不足时不能公开正文。目前只有实际比较通过、选中了新稿、且父级证据完整的失败 `REVISE`，才能经此入口继续修订。落败修订仍保留为诊断证据，不能替换原基准，也不能经此入口成为下一轮基准。盲读者与独立评审只收到各自允许的新稿输入。修订不自动接受、结算或发布章节。

## 6. 候选稿演进不能污染全新重生成

质量演进通过已登记的语义比较评估基准稿与挑战稿。候选稿谱系记录挑战稿是修订稿、全新重生成稿还是用户编辑稿。修订稿的文本父级等于比较父级；全新重生成稿仍然有比较父级，但文本父级必须为空。

## 7. 对精确候选稿执行独立评审

质量门要求独立性时，先冻结并打包已经合格的候选稿，记录检查点，再派发给真正独立且具备所需能力的调用或会话。返回结果必须绑定同一份候选稿指纹，校验后只能消费一次。有效拒绝必须回到修订流程，不能通过不停更换评审者来规避判断。

<img src="assets/concepts/independent-semantic-review.zh-CN.svg" alt="管理器调用与评审调用彼此分离，只通过带内容指纹的候选稿制品连接" width="100%" />

## 8. 对用户可见的交付门

只有适用的语义检查、连续性检查、谱系检查和独立性要求全部解决后，候选稿才可以按当前契约称为评审稿或具备生产交付条件。用户或编辑的接受是另一项决定；状态落定又是另一项经授权的状态修改事务。
